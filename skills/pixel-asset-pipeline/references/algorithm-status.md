# 算法流程、实测效果与经验

记录日期：2026-10-30。本页整理已有代码与冻结验收记录；本次文档更新没有生成图片、重跑算法、调整阈值或修改算法代码。结论只覆盖已检查的样本与版本。

当前定位：**可重复的像素素材预处理工具，尚不是通用的自动像素画精修器。** 网格、透明度和导出已有明确技术保证；青紫污染、轮廓节奏与未知材质原色仍存在不能自动可靠判断的情况。

## 实际包含哪些流程

| 路线 | 处理顺序与用途 | 本仓库的交付范围 |
|---|---|---|
| 独立本地引擎 v0.2.1 / recipe 2 | 背景检查／去底 → 固定网格中心取样 → 源图证据去污染与补色 → 明确材质精修 → 色块整理 → 明确竹木轮廓 → 原生 PNG | 包含代码，可独立运行 |
| Studio 默认固定流程 | 原图 → 语义／色键抠图 → 固定网格 → 去污染 → 碎色整理 → 自动精修 → 源图背景／前景色恢复 → 原生导出 | 包含调用客户端；需要已有兼容服务 |
| Studio Proper 完整流程 | 不透明原图 → proper-pixel-art 原生网格、配色与透明处理 → 源图约束清理 | 可选实验模式；引擎未随本仓库打包 |
| Studio Proper 混合精修 | 旧固定网格结果＋原始 RGB＋原始 matte＋实际采样记录 → Proper 提供颜色参照 → 局部混色恢复 → 原生导出 | 可选服务模式；不是当前 CLI 默认流程，也未打包为独立引擎 |

生图客户端可以请求 `nano-banana-2` 或自定义 Images／Gemini API。它不托管模型；模型列表里存在某个名称，不代表当时一定有可用通道。生图失败必须报告实际失败，不得把替代模型的结果写成 Banana 成果。

### 独立本地引擎

默认最长边 256；也可指定完整逻辑画布，或用 `--native` 保留输入尺寸。网格按源图单元的一致中心位置取样，再整理色板；不再用各格精确 RGB 频次投票。后者容易把抗锯齿、多色细线变成断点，尤其是门窗与竹杆。

透明度为 0／255，透明像素 RGB 清零；显示放大使用整数最近邻。默认 96 色是预算，不是最终色数硬上限。保留原色的回退和后续恢复可能增加颜色，不能宣称“最多 96 色”。低于逻辑分辨率的细线仍可能在采样时丢失。

recipe 2 关闭了去污染后的全局键色残色删除。没有充分源图证据的青紫色会保留；初始色键或相连背景色判断仍可能误删与底色相同的前景。哈希匹配的完成侧车用于避免反复推理、压色和移动轮廓。改变参数要回原图，而不是不断处理上一张导出图。

### Studio 默认恢复

`pixel_studio.py run` 不传 `--profile`，请求服务的默认自动流程。既有已验证服务执行最终阶段 `source-backed-final-background-refinement-v4`，其中原色恢复规则为 `source-connected-material-endpoint-restoration-v5`。实际执行版本以 `run-report.json` 的 `processingStages` 为准；更新 skill 不会替换旧服务的算法。

这一阶段使用原始源图、保存的去底 matte、采样位置与可见材质路径，区分已有背景决策和待恢复的前景颜色。证据不足时跳过；恢复 RGB 的后缀不能补回上游已经删掉的前景。显式 `--profile` 是另一套材质流程，不是开启默认恢复的开关。

### 为什么保留 Proper 混合方案

实测 Proper 完整流程确实调用了 proper-pixel-art 2.0.0，但其实际网格并不等于请求的目标值：茉莉 243×247、蕨叶 301×305、玻璃灯 279×302。茉莉有改善；蕨叶比旧 256 网格出现更多碎阶梯与色斑；灯内部粉紫色仍在。因此它保留为可选实验，没有替换默认流程。

混合方案取两边有用的部分：**冻结旧网格和全部 alpha，借用 Proper 与旧流程中有源图支持的干净材质颜色参照。** 它不使用 Proper 网格重新缩放旧素材。清理只改 RGB，因此旧输出中的细杆、孔洞、留白和锚点保持；旧遮罩自身的错误也会保留。

恢复使用局部颜色端点与键色混合残差，形式为 `C = (1-t)F + tB`。在独占背景策略下，还会按内部深度、颜色端点和残差条件自动尝试连续中性色调恢复，避免用一个灰色填满玻璃。当前接口没有玻璃材质或区域标注参数；这是有条件的中性材质先验，不是自动识别出玻璃的语义证明。这里使用项目自己的数值恢复，并非调用 PyMatting 或某个通用神经精修模型。

两种策略必须区分：

- `conservative`：默认策略，要求源单元有实际前景／背景混合证据，优先保护真实青紫材质。
- `exclusive-background`：显式约定“背景键色族仅用于底图”。它允许更强的内部混色恢复；若物体本来使用相同青紫色，这个约定就不成立，可能误改原色。

玻璃灯的大幅改善依赖后一种约定及中性玻璃先验，不能推广成对任意彩色玻璃都能自动正确还原。

| 状态 | 结论与边界 |
|---|---|
| 技术机制已建立 | 固定逻辑网格、硬 alpha、透明 RGB 清零、原生 PNG、整数最近邻预览与完成记录保护；这些不等于美术质量合格 |
| 特定版本／样本已验证 | 混合阶段冻结 alpha，保留三张底稿的孔洞和细杆；只涉及这一阶段，不保证上游遮罩从未漏删 |

| 尚未可靠解决 | 蕨叶亮青／暗青残块、少量粉紫边格、弱混色、远离干净参照的内部污染、未知绿叶的正确颜色端点 |
| 尚未自动解决 | 所有外轮廓的台阶节奏、粗细统一、低分辨率细线丢失、错误遮罩的语义修复、任意 AI 图自动达到手绘生产质量 |
| 尚未包含 | 独立引擎中的最新 Studio 混合代码、完整 Studio 应用、模型权重，以及真正的瓦片接缝／自动地形规则／Godot `.tres` 导出 |

灰／奶油色在附近有可靠干净参照时，12 个已知混色测试区精确恢复。真实青紫细环紧邻透明孔洞、真实粉花、已知绿／竹／白色和一像素杆的保守保护检查也通过。

同时保留失败记录：参照超过局部范围（16 原生像素）时会跳过或恢复不足；部分绿色混色会选中仍轻微受污染的冷绿端点；弱混色可能无法区分。两个较复杂的独占背景综合测试仍是 `allPass:false`。这不应被“若干测试通过”掩盖，也不能用青紫阈值计数声称污染清零。

## 经验与后续判断原则

1. **分割与去污染分开验收。** 去掉 alpha 背景，不会自动移除已经混进前景 RGB 的底色；删除异色也不等于恢复材质。
2. **色值残差有用，但需要端点证据。** 单张不透明 RGB 可以由不同前景色和混合比例解释。局部干净颜色、源 matte 与素材约定能减少歧义；残差小本身不能证明语义正确。
3. **正确采样优先于反复平滑。** 先冻结源图与逻辑网格，避免重新划格带来额外碎阶梯。中心取样也不是万能细线保护，必须同时检查结构。
4. **保留真实反例。** 测试要同时包含受污染颜色和真实青紫材质，尤其是靠近孔边的细环；只检查物体深处的纯色不足以证明没有误改。
5. **不默认全局删色、3×3 众数或强制纯黑描边。** 这些可降低杂色计数，也会吞掉细杆、孔洞、局部高光和原有彩色轮廓。局部操作应受源图与结构约束。
6. **算法实际执行不等于效果胜出。** Proper、perfectPixel、unfake、Spritefusion 等名称不能代替同坐标局部比较；本仓库不承诺把这些全部打包成可独立运行的默认引擎。
7. **比较固定输入、版本与坐标。** 保存原图、matte、采样 cuts、输出哈希；看全图、局部整数放大及 alpha。改色数、色数和连通性是辅助证据，不是通用美术分数。
8. **自动化允许有依据地保留不确定项。** 通用规则应跨素材验证，不能将逐图坐标补丁提升为默认算法。还需更广泛、带原色真值的混色样本验证，不能仅靠同三张图反复看起来更干净。

下一步若继续开发，应优先评估带干净原色真值的成对混色基准、错误端点拒绝与置信度分流，再考虑更强模型；这些是后续方向，本次没有实现或运行。
